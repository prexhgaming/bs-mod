# Project notes

## What this is
- **BS-KILLER** — a single-game launcher built on the **BlackBox virtual engine** (Android app cloning / sandboxing SDK).
- Engine source: `github.com/Black00Z/Blacks-BlackBox`. `Bcore/`, `black-reflection/` and `compiler/` are vendored from it; `app/` is this project's own code.
- Target game is hard-wired in `app/.../GameTarget.kt` (`com.netease.newspike`, "Knives Out", sandbox user 0).

## Modules

- `:app` — Kotlin UI (`zyn.bs`). Launcher activity = `.view.game.GameActivity`, `Application` = `.app.App`.
- `:Bcore` — engine: Java (`zyn.bs.core.BlackBoxCore`), AIDL (`Bcore/src/main/aidl`), native C++ (`Bcore/src/main/cpp`). No prebuilt `.so` — compiled from source by the NDK.
- `:black-reflection` — annotation/reflection stubs required by `:Bcore`.
- `:compiler` — annotation processor for `:black-reflection`.

## Launcher UI (`:app`)
- One screen, one game, one action. The old multi-app grid/list is gone — do not reintroduce an app list or multi-app selection.
- Full-bleed wallpaper is `app/src/main/assets/1795549016113.jpg`, decoded at runtime in `GameActivity.decodeWallpaper()` (downsampled to screen width, RGB_565) and darkened by `bg_hero_scrim` + `bg_hero_vignette`.
- **GMS is invisible by design**: Play services are cloned by `GameRepository.provision()` (game first, then GMS) but must never appear as a chip, row, icon, menu item or status line. Provisioning stages use generic wording only (`launcher_stage_*`). The one deliberate exception is a **failed** clone: it surfaces through the existing error banner (`SandboxStatus.gmsError` → `GameActivity.renderNotice`), because a silent failure looked identical to success and only showed up as an in-game "Play services are missing".
- **Split-bundle detection trap (fixed — do not reintroduce)**: `GmsCore.installGApps` clones the *device's* Google packages through `installPackageAsUser` → `BPackageManagerService.installPackageAsUserLocked` → `isApksBundle()`. The old content fallback counted **any** two `.apk` entries anywhere in the zip, and GMS's `base.apk` embeds its dynamite modules as `.apk` files in assets — so GMS was "installed" as `com.google.android.gms.policy_ads_fdr_dynamite` (`AdsDynamite.apk`) while real `com.google.android.gms` never entered the sandbox. `isApksBundle` now treats `AndroidManifest.xml` at the archive root as proof of an ordinary APK, and requires `toc.pb`/root-level split APKs for a bundle. Recognise the symptom by `Settings: loaded Package:` listing `gsf`/`vending` but **no** `com.google.android.gms`, with the game logging `GooglePlayServicesUtil: ... they are missing`.
- `installGApps` installs GMS/GSF first (`GOOGLE_CRITICAL` via `LinkedHashSet` — it used to be an unordered `HashSet`) and only reports those two as fatal; a peripheral failure (wearables, feedback, setupwizard, or a 32-bit-only APK rejected by `AbiUtils.isSupport()` on a 64-bit box) is logged and skipped, instead of `uninstallGApps` wiping the whole set on any single failure.
- `GmsProxy: Failed to get gms service binder` is **benign** — it probes for a `"gms"` binder in the real servicemanager, which normally has none. Don't chase it when debugging GMS.
- **GMS signature verification is what actually gates Play services (fixed — do not regress)**: with the clone working, the next failure is `GoogleSignatureVerifier: package info is not set correctly` → `GooglePlayServicesUtil: ... requires Google Play Store, but its signature is invalid` → `DynamiteModule: Invalid GmsCore APK, remote loading disabled` → every `GoogleApiManager` service failing with `ConnectionResult{statusCode=SERVICE_INVALID}`. `IPackageManagerProxy.GetPackageInfo` used to return `createFakeGooglePlayServicesPackageInfo()` — a synthetic `PackageInfo` with **no `signatures`/`signingInfo`** — and only borrowed the host's certificates behind an opt-in `host_signing_fallback` pref that defaults to **false**, so GMS could never work out of the box. It also reused the *caller's* flags when reading the host package, and a request with `flags = 0` carries no certificates at all, so there was nothing to copy. Now: the vending fake always borrows the host's real signatures, and any Google package that comes back without certificates gets them attached too, via `tryGetRealHostPackageInfoWithSignatures()` which **forces** `GET_SIGNATURES` (`0x40`) plus `GET_SIGNING_CERTIFICATES` (`0x08000000`, API 28+). A fabricated certificate can never match Google's embedded certs, so borrowing the real one is the only thing that works — and package signatures are public (any app can read them), so there is no privacy trade-off. Related: `BPackageManager`'s stub must leave `signatures` **null**, not `new Signature[]{}` — both fail verification, but the empty array makes `signatures[0]` throw `ArrayIndexOutOfBoundsException`.
- **GMS also needs `listenForNetwork`**: `IConnectivityManagerProxy` had `registerNetworkCallback` hooked but not `listenForNetwork`, and the real `ConnectivityService` rejects `com.google.android.gms` because that package is not owned by the sandbox's (host) uid — `SecurityException: Package com.google.android.gms does not belong to <uid>`. GMS drives its connectivity state machine through those callbacks, so it never learned whether the network was up. The hook rewrites the package argument like the neighbouring proxies do.
- **Runtime permissions belong to the HOST app**: the cloned game runs in this app's process and uid, so the OS checks *this* app's permissions — one the launcher lacks is one the game lacks. `Bcore`'s manifest already declared `RECORD_AUDIO` (merged into `:app`), but nothing ever *requested* it, and a dangerous permission stays denied until prompted; that is why the in-game mic was silently dead. `GameActivity.requestGamePermissions()` now asks once in `onCreate` for `RECORD_AUDIO` (+ `POST_NOTIFICATIONS` on API 33+), skipping anything already granted, and never blocks or nags on refusal. Declaring a dangerous permission in the manifest is **not** enough — and `POST_NOTIFICATIONS` is declared by `:app` itself, not inherited.
- Entry animation, breathing halos and the CTA light sweep are plain `ValueAnimator`/`ViewPropertyAnimator` (alpha/scale/translation only). Cancel them in `onDestroy`.
- The engine's `ClientConfiguration` in this SDK has no `isHideXposed()`; overriding it breaks the Kotlin build.

## Native mod menu (`libzyn-bs`)
- Sources are the uploaded `src.zip` (`main/jni/**`), dropped in **verbatim** at `app/src/main/cpp/**` → `libzyn-bs.so`. Keep the odd `小鱼字体.h` (6.7 MB CJK font, included under that raw name by `draw.h`). Only four files are *not* byte-identical to the archive: `Android.mk` + `Application.mk` (see below), `main.cpp` (the game-build hook offset — the uploaded one carries a stray `HOOKI(addr,, func)`, whose 2-arg macro silently cannot expand) and `xhook/xh_util.c` (runtime page size — see the 16 KB note below). Keep local edits to upstream files that small and listed here.
- Built with **ndk-build**, using the archive's own `Android.mk` + `Application.mk` as the **single build description** (STL, ABIs, API level, 16 KB pages, all flags live there), wired through `android.externalNativeBuild.ndkBuild` in `app/build.gradle` (top-level `android {}` block, **not** inside `buildFeatures {}`). There is **no CMakeLists.txt and it must not come back**: `arguments(...)` is not a valid method on the top-level `externalNativeBuild.cmake` block (`CmakeOptions`), and two parallel build descriptions are how source lists drift. Adding a source = editing `LOCAL_SRC_FILES` in `Android.mk` only.
- `LOCAL_MODULE := zyn-bs` is what names the output `libzyn-bs.so`; `Application.mk`'s `APP_MODULES := zyn-bs libdobby` builds **only** the menu, so the `injector` module is skipped while the prebuilt Dobby static lib is still built as a dependency.
- `injector.cpp` ships for archive fidelity but is **not compiled** (kept out via `APP_MODULES`): upstream it is a second module (`libinjector.so`) exporting `Java_com_nexora_InjectorActivity_*`, i.e. the client half of a separate ptrace-injector app. This sandbox does its own injecting.
- **Exactly one load site**: `BlackBoxLoader.afterApplicationOnCreate` (guest process, package must equal `GameTarget.PACKAGE_NAME`) → `util/ZynBs.kt` → `System.loadLibrary("zyn-bs")`, guarded by a `/proc/self/cmdline` check and a `catch (Throwable)` so a bad `.so` can never stop the game. Never load it from `App.onCreate` (host process) and never add a second site.
- Nothing crosses JNI in either direction: no `external fun`, no reliance on `JNI_OnLoad`. `main.cpp`'s `__attribute__((constructor)) void __0__()` detaches a worker thread and returns, so the game's main thread never blocks — that is also why no Java call is needed after `loadLibrary`.
- The overlay needs no NativeActivity: `AImGui/NativeActivityHelper.cpp` fabricates an `ANativeActivity` by reflecting `ActivityThread.mActivities` / `currentActivityThread`.
- Dobby ships prebuilt archives for **arm64-v8a + armeabi-v7a only** (`Dobby/libraries/<abi>/libdobby.a`); adding an x86 ABI fails at **link** time, not compile time. Only **`armeabi-v7a` is built** (see the next line).
- **32-bit only on purpose**: the game is an `armeabi-v7a` library and a 64-bit process cannot load it, so shipping `arm64-v8a` would let the sandbox spawn a 64-bit process the game can never map into. `abiFilters` in `app/build.gradle` and `APP_ABI` in `Application.mk` are both `armeabi-v7a` and must be changed together. Consequence: 64-bit-only devices (recent Pixels) cannot install the APK.
- Two flag traps worth keeping: `-D__BIONIC_NO_PAGE_SIZE_MACRO` hides libc's `PAGE_SIZE`, so hardcoded-4096 page math fails at compile time instead of corrupting memory on 16 KB devices — that trade is **deliberate**, and the answer to a resulting error is to switch the code to `sysconf(_SC_PAGE_SIZE)`, not to delete the flag. Vendored `xhook/xh_util.c` used to be the one offender (it relied on the removed `PAGE_SIZE`/`PAGE_MASK` macros); it now derives both from the runtime page size, like `KittyMemory.h`'s `_SYS_PAGE_SIZE_`, `include/includes.h` and `include/ori.h` always did. `-fpermissive -fexceptions` are required by the upstream dialect. The archive's `-latomic` is **deliberately dropped** — the NDK removed libatomic in r23, so it would only produce a "non-system library" warning and a link error. `Application.mk` asks for `APP_PLATFORM := android-24`, but AGP passes `APP_PLATFORM=android-21` (from `minSdk`) on the command line, which wins; harmless here because nothing in the sources is newer than API 9 (`__system_property_get`, `ANativeWindow_setBuffersGeometry`).
- **ImGui has ONE global context and it can be null at any time**: `draw.h`'s `Draw()` (hooked on `eglSwapBuffers`) creates it, `AImGui::BeginFrame` swaps in the one AImGui made, and `AImGui::UnInitEnvironment()` destroys it — `DestroyContext()` leaves the current context null. The input hooks run on the game's **own input thread** and fire in every one of those windows, while `ImGui::GetIO()` is literally `IM_ASSERT(GImGui != nullptr); return GImGui->IO;` and the assert compiles out in release — so a tap before the first frame rendered (or during teardown) dereferenced null and killed the process. Every foreign-thread ImGui entry point must pass `nx::imguiInputSafe()` from `include/hpp/imgui/ctx_guard.h` first: `initializeMotionEvent` (`include/input.h`), `AInputQueue_getEvent`, and `TrackImGuiWindow`/`IsImGuiTouchPoint` (`include/hpp/imgui/touch.h`). Readiness is published only after the font atlas exists (in `draw.h` `setup = true` is deliberately the last step) and retracted by `imguiBeginTeardown()` at the start of both `AImGui::UnInitEnvironment()` and `OnExit()`. Never cache the context pointer — it can be destroyed between two calls.
- **`PyRun_StringFlags` offset is KNOWN: `0x024dbcf0`** (`kNexoraPyRunOffset` in `main.cpp`, Thumb, 0x64 bytes, verified against the shipped `libGame.so`). Setting it non-zero makes `py_hook_thread` hook it directly (the runtime scan is gone). **How it was found, so it can be redone on a game update** — the two scan strategies in `find_pyrun.py` were tried and *do not work* on this build, so the script is kept as a diagnostic: (A) call-site voting over `movw r1,#0x101` is useless here (134 sites, top vote only 5) and (B) a `"<string>"` xref finds nothing, because CPython reaches that literal through a `.got` slot for `_PyRuntime` (`LDR r0,[pc,#imm]; ADD r0,pc; LDR r0,[r0]; ADD.W r5,r0,#imm`), and `.got` pointers are absolute-at-load, so a prel31/relocation sweep keyed off the *pool* address misses them systematically — the ADR addend is relative to the **ADD instruction**, not the pool word. What *did* work is the call signature: every caller passes `(str, start, globals, locals, flags)` with `globals == locals`, so `r2 == r3`, and `PyRun_SimpleStringFlags` also hardcodes `start = 257`. Scanning the whole `.text` for a `BL` whose `r1` was loaded with `movw #0x101` **and** whose `r2`/`r3` came from the same register yielded exactly ONE function in 84 MB. Confirm a candidate by structure: 5 args saved off `r0..r3`+`[fp,#8]`, `PyArena_New` (NULL-checked), a 2nd call with `(…, flags, arena)`, `PyArena_Free`, return. Its callees sit in CPython's `pythonrun.c`/`arena.c` cluster (arena helpers at `0x024d63ac` / `0x024d641a`).
- Reading ARM32 Thumb `MOV`-register: `0100 0110 D Rm Rd` where `Rd = (D<<3)|Rd3` — e.g. `0x4629` is `MOV r1, r5`, **not** `MOV r1, r9`. Getting that wrong makes a correct function look wrong.
- **`app/src/main/cpp/find_pyrun.py`** is the reusable offset-finder: scans `.text` for `movw r1,#0x101` seeds, follows each to the next `BL`, resolves `r2`/`r3` sources, and keeps candidates where `r2 == r3`. Run `python3 app/src/main/cpp/find_pyrun.py libGame.so --top 5` and set `kNexoraPyRunOffset` to the best strict-match address. It runs in ~1.2 s on the 84 MB library.
- **Dead ends already ruled out on this binary** (don't repeat): `0x471e320` (the offset in the uploaded archive) is in `.data`, not `.text` — `.text` ends at `0x417e724`, so it was never valid for this build. CPython symbols are stripped (only `PyInit__testinternalcapi` survives, at `0x0235bf6d`, odd ⇒ Thumb). There is no `.rel.dyn` entry for the token-name table slot, and `"<string>"` appears only in CPython's token-name array, not in `PyRun_StringFlags`' own reference.
- **The old one-shot injection was a real bug**: it set `loaded = true` *before* the injection returned, so one early `ImportError` (the game's `gclient.*` framework is not importable at the 2nd script) silently killed the mod for the whole session. Injection now runs a self-contained, never-raising probe on calls 2,4,8,…,1024 that writes a marker file, and injects `srcpy` only once that marker appears; a NULL return reopens the state machine so it retries instead of giving up. Keep the marker-file handshake — the probe cannot signal success any other way.
- The script injected by that hook (`include/cpp/srcpy.cpp`) is **not** a memory reader — it is a monkey-patching mod with ~34 `@HOOK(...)` decorators that `setattr` onto live game classes, and it imports the game's own Python framework (`gclient.*`, `gshare.*`). This is why a statically embedded CPython is **not** a substitute: a private interpreter would have none of those modules and would `ImportError` on the first import line. Do not try to "fix" the script by embedding a runtime.
- The `SDK/libGame_SDK.py` + `SDK/Python/*.py` offset dump is **unrelated to the script running** (`srcpy.cpp` references none of it) and it is itself partly corrupt (57 of 703 modules fail `py_compile`, `libGame_SDK.py` has a syntax error). It is 64-bit-derived and is only useful as a structural reference. Do not treat its condition as a blocker for the mod.
- `iMissMyWife` no longer injects blind on call #2 (see the injection note above); `iLoadAt` is gone. If the mod still does nothing, check logcat for `python probe at call N` / `python framework ready at call N` / `srcpy loaded at call N` and `hook confirmed:` before assuming the address is wrong.
- Picks its process by the `newspike`/`newspikeme` names (`PACKAGE_NAME` from `/proc/self/cmdline`).
- The menu stores config in `/data/data/<game-pkg>/imgui` (internal storage → **no permission**; do not add `MANAGE_EXTERNAL_STORAGE`/`WRITE_EXTERNAL_STORAGE`). `NetworkBlocker.hpp` hooks the **game's** `getaddrinfo`/`gethostbyname`/`connect`, which the game already holds `INTERNET` for.
- Engine gotcha: the sandbox redirects `SharedPreferences` into the game's own virtual data dir, so host and guest processes read *different* prefs files. Any decision shared between them must live in a file the guest can read, not in prefs.
- Removed by this swap — do not resurrect: the Python SDK dumper (`sdk_dumper.cpp`, `py_runtime_dump.cpp`, `native_utils.cpp`, `third_party/`, `util/PySdkDumper.kt`) and its More-menu toggle (`action_dump_sdk`). `uploads/` (reference material, e.g. `src.zip`) and `tmp/` (scratch rigs) are gitignored.

## Crash handling
- **There is no custom crash handler, and no engine crash-suite — both were deliberately removed. Do not reintroduce either.**
- An app-side `CrashHandler` + `:crash` `CrashActivity` pair existed and was deleted. The engine's "crash prevention" set (`CrashMonitor`, `SimpleCrashFix`, `StackTraceFilter`, `NativeCrashPrevention`, `DexCrashPrevention`, `SocialMediaAppCrashPrevention`, `core/CrashHandler`) is still on disk but **unhooked**: no call sites remain in `BlackBoxCore`'s static init, `BlackBoxCore.installSystemHooks()`, or `BActivityThread.handleBindApplication()`. Fatal exceptions must propagate normally.
- **Why the suite is an ANR trap (do not re-enable)**: `CrashMonitor.installGlobalCrashHandlers()` swallowed every uncaught exception and never rethrew — so a fatal main-thread exception left the Looper dead and Android reported *"not responding"* instead of a clean crash. Separately, `CrashMonitor.startPeriodicHealthChecks()` did file I/O and reflection on the **main** handler every 30 s / 60 s, and `DexCrashPrevention` hashed the APK periodically. That combination is why the hang showed up *minutes into gameplay* rather than at launch: the game hits an exception, nothing dies cleanly, and the next main-thread poll stops being serviced.
- `release` has `minifyEnabled true` + `shrinkResources true`. Safe because nothing resolves resources by name (`Resources.getIdentifier` appears nowhere); the engine's reflection needs are covered by `proguard-rules.pro`.

## Toolchain
- Gradle wrapper 8.13, AGP 8.13.2, Kotlin 1.9.23, JDK 17, `compileSdk 35`, `targetSdk 28`, `minSdk 21`, `ndkVersion 29.0.13846066`, ABI `armeabi-v7a` (32-bit only — see the mod-menu section).
- **The wrapper version and AGP must move together**: AGP 8.13 refuses to apply on Gradle < 8.13 (`Minimum supported Gradle version is 8.13`). Bumping `agp` in `gradle/libs.versions.toml` without bumping `distributionUrl` in `gradle/wrapper/gradle-wrapper.properties` fails at configuration time, before any compilation.
- **Java target must stay 17**: CI installs JDK 17, so `compileOptions { VERSION_21 }` in any module fails with `invalid target release: 21`. `app` and `Bcore` are both on 17 to match. If Java 21 is ever needed, bump `java-version` in `.github/workflows/release-apk.yml` first.
- `compileSdk`/`targetSdk`/`minSdk` live in root `build.gradle` (`ext.*`). `compileSdk 37` fails — the CI runner has no `platforms;android-37`.

## Building — NOT possible in this sandbox
- The sandbox has **no JDK and no Android SDK/NDK**, so `./gradlew` cannot verify anything here — a native or Gradle mistake only surfaces on CI, so keep native-build edits conservative and push to check.
- Build on CI (`.github/workflows/release-apk.yml`: JDK 17 + `setup-android`, `assembleRelease`, Telegram notifications) or locally in Android Studio.
- Repositories are plain `google()` / `mavenCentral()` / JitPack — **no Aliyun mirrors** (they return 502 and abort resolution).
